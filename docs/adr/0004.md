# ADR-0004: Testing strategy

- **Status:** Accepted, amended by ADR-0007
- **Date:** 2026-10-02

## Context

I have little experience writing tests, and learning to test is an explicit goal. The code calls paid, slow and non-deterministic model APIs, which must not be called from ordinary test runs. The AI reviewer cannot execute code, so tests are the only automated check of behaviour.

## Decision

Three layers of tests, run with Vitest:

1. **Core unit tests (most tests).** The agent loop, permission policy and context management, tested with `FakeProvider` and fakes for other ports. No network, no real filesystem, deterministic.
2. **Adapter contract tests.** Real provider responses recorded once and stored in `test/fixtures/`, then replayed through the adapter's parser. They check that real streaming output becomes the correct canonical events, without calling the API.
3. **Tool integration tests.** File and shell tools run against a temporary directory, checking the real effect on disk.

Conventions:

- Unit tests live next to the code they test (`agent-loop.ts` and `agent-loop.test.ts`). `test/` holds only shared fixtures and helpers.
- I write the tests myself. Workflow: red → green → refactor (write a failing test, make it pass, then clean up).
- Every review includes a list of missing test cases, with the failure each one would catch.
- **CI** (GitHub Actions, Ubuntu) runs typecheck, lint and tests on every push. A change is reviewed only after CI passes.
- **No real API calls in CI.** Any test that hits a live API is opt-in, behind an environment variable, and excluded from the default run.

## Alternatives considered

- **Mocking `fetch` everywhere instead of fakes behind ports.** Couples tests to HTTP details, so they break whenever an adapter's internals change. Fakes at the port level test behaviour instead.
- **End-to-end tests against real models as the main safety net.** Slow, costly, flaky. Useful later as the eval project, not as unit tests.
- **Strict test-first TDD for everything.** Good discipline, but rigid while I'm learning. Test-first is the default for the core, and allowed to slip for exploratory adapter work, with tests added before merge.

## Consequences

- The ports from ADR-0001 are what make layer 1 possible. If something in the core is hard to test, that's a design signal, not a reason to skip the test.
- Recorded fixtures go stale when providers change their output. Re-record when contract tests start failing against live runs.
- Fixtures must never contain API keys or private data. Check before committing.
- No coverage target for now. Coverage measures lines executed, not behaviour verified, and a target encourages tests written for the number.
