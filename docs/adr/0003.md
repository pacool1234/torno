# ADR-0003: Provider strategy

- **Status:** Accepted, amended by ADR-0007
- **Date:** 2026-10-02

## Context

torno must work with models from several vendors, and the later eval project must compare models fairly. Budget is limited, so development should cost little or nothing.

A port designed from a single implementation tends to copy that implementation's shape. A provider abstraction is only trustworthy once at least two genuinely different protocols implement it.

## Decision

Three `ModelProvider` adapters, built in this order:

1. **Anthropic Messages protocol (Phase 1).** Content blocks, `tool_use` / `tool_result`, explicit cache control, a rich streaming event structure with tool arguments arriving as partial JSON.
   - **Written with raw HTTP:** `fetch` plus a hand-written parser for the event stream. No vendor SDK.
   - **Developed against Ollama running inside WSL2** (v0.14.0+ accepts the Anthropic Messages format), at zero cost.
   - **Validated against 5–10 recorded real Anthropic responses**, stored as fixtures. Ollama emulates the protocol and may differ in streaming details.
2. **FakeProvider (Phase 1).** Replays scripted responses. Used by most tests.
3. **OpenAI-compatible protocol (Phase 2).** Flatter message shape, tool-call fragments matched by index. Covers OpenRouter, DeepSeek, Kimi and local models.

The **canonical message model** in `src/core/` is block-based, closer to Anthropic's shape, because it can represent everything the flatter format can.

**The port is expected to change when the second real adapter lands.** That is the purpose of building it, not a failure of the first design.

## Alternatives considered

- **OpenRouter only.** One adapter reaches hundreds of models, but there's only one protocol, so the abstraction is never tested, and much of the protocol learning is lost. Kept as a target of adapter 3 instead.
- **Official vendor SDKs.** Faster to a working loop, but they hide streaming and tool-call assembly, which are core learning goals.
- **Direct Anthropic API for development.** Real behaviour, but every iteration costs money. Reserved for recording fixtures and later behavioural testing.

## Consequences

- Development defaults to FakeProvider and local models. Paid APIs use prepaid credits with auto-reload off.
- Provider and model are configuration, not code. The base URL is configurable, so the same Anthropic adapter can point at Ollama or at Anthropic.
- For reproducible evals through OpenRouter, the adapter must support pinning the upstream provider (`provider.order` with `allow_fallbacks: false`, and `require_parameters: true`). Required by Phase 4.
- Caching behaviour differs per provider (automatic vs explicit breakpoints). The context manager will need to know which applies. Phase 3.
- Cost comes from each provider's usage data where available (OpenRouter returns cost per response). Otherwise it's computed from a price table, which goes stale.
- Raw HTTP means I own everything an SDK would handle: event-stream parsing, partial-JSON assembly, retries with backoff, timeouts, cancellation, and error mapping. That's the learning goal, and also the main source of Phase 1 bugs, so each item needs tests.
- Running Ollama inside WSL2 keeps everything on one network (`localhost`). Reachability must be verified before Phase 1 starts.
