# ADR-0005: Sandboxing, applied by phase

- **Status:** Accepted
- **Date:** 2026-10-02

## Context

torno executes commands and edits files based on model output. Models make mistakes, and they can be manipulated: text in a README, an issue or a web page can instruct the model to run a command or reveal secrets (prompt injection). The agent runs as my user, with access to everything my user can reach, including SSH keys and `.env` files.

Sandboxing limits what a command can reach, so a bad command can only do bounded damage.

| Level | Mechanism                                                     | Strength                     |
| ----- | ------------------------------------------------------------- | ---------------------------- |
| 1     | Permission prompts with an allowlist                          | Weak alone: approval fatigue |
| 2     | Path confinement in the file tools                            | Cheap; `bash` bypasses it    |
| 3     | OS-level sandbox for the shell process (bubblewrap, Landlock) | Strong, Linux-specific       |
| 4     | Container (Docker)                                            | Strongest practical option   |

## Decision

Apply the levels by phase:

- **Phase 2: levels 1 and 2.**
  - Every `write`, `edit` and `bash` call requires approval, unless it matches a user-configured allowlist. Reads are allowed inside the project root.
  - File tools resolve every path (`..`, symlinks) to its real absolute path and refuse anything outside the project root. The check runs on the resolved path, not on the string the model sent.
  - In headless mode there is no human to ask, so permissions come from a policy. **The default policy denies.**
- **Phase 4: level 4 for eval runs.** Each eval run executes the agent inside a Linux container with only the task repo mounted.
- **Phase 5: level 3 evaluated** for interactive use.

## Alternatives considered

- **Container from day one.** Strongest isolation, but it adds Docker to the development loop before the agent even works, and makes debugging harder.
- **Prompts only.** Simplest, but approval fatigue makes it unreliable over long sessions.
- **Trusting the model (no gates).** Unacceptable for a tool that runs shell commands from model output.

## Consequences

- **Known limitation, accepted for Phases 2–3:** `bash` bypasses level 2. `cat ~/.ssh/id_rsa` never touches the file tools. Until level 3 or 4 applies, the permission prompt is the only gate on shell commands, so `bash` is never on the default allowlist.
- Path confinement has classic pitfalls: symlinks pointing outside the root, a check on the string followed by use of a different path (time-of-check vs time-of-use), and prefix matching (`/home/me/torno-evil` starts with `/home/me/torno`). Each needs a test.
- Secrets: `.env` sits inside the project root, so level 2 alone does not protect it. Decide in Phase 2 whether file tools deny it by default.
- The permission policy is a port (`Approver`), so the REPL asks the user while headless mode applies a configured policy, with no change to the core.
