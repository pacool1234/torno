# ADR-0002: TypeScript (strict) on Node LTS, developed in WSL2

- **Status:** Accepted
- **Date:** 2026-10-02

## Context

My strongest language is JavaScript, with some TypeScript. The project's goals are learning agent mechanics and software architecture, and producing a portfolio piece for AI engineering roles.

Candidates considered: TypeScript, Python, C#.

## Decision

- **Language:** TypeScript with `strict: true`.
- **Runtime:** Node.js, current LTS version, installed inside WSL2 via nvm.
- **Test runner:** Vitest.
- **Module system:** ESM only (`"type": "module"` in `package.json`).
- **Runtime validation:** Zod, used at trust boundaries (see Consequences).
- **Package manager:** pnpm.
- **Lint and format:** ESLint with typescript-eslint in type-checked mode, plus Prettier for formatting.
- **Platform:** Linux. Developed in WSL2 with the repo in the Linux filesystem (`~/code/torno`). CI runs on Ubuntu. Native Windows is a non-goal (see `VISION.md`).

## Alternatives considered

- **C#.** Interfaces and dependency injection map naturally onto ports and adapters, but it isn't my strongest language, so attention would go to the language instead of the design. Smaller AI-tooling ecosystem.
- **Python.** Strong AI ecosystem, and my first agent was in Python. But TypeScript is closer to my daily skills, and its type system gives the compiler a bigger role in catching design mistakes.
- **Bun or Deno instead of Node.** Faster startup and built-in tooling, but Node is the default for CLI tools and for the AI tools I'll compare against. Switching later is cheap if the core stays free of runtime-specific APIs.
- **npm instead of pnpm.** Ships with Node and needs no setup, but its flat `node_modules` allows importing undeclared packages (phantom dependencies). pnpm's strict layout prevents that, and its workspaces suit a possible monorepo with the eval harness.
- **Biome instead of ESLint + Prettier.** One fast tool with minimal configuration, but its type-aware rules are younger: at launch (June 2025) its floating-promises rule caught about 75% of what typescript-eslint catches. In heavily async code, unawaited promises are among the most likely bugs, so the more thorough checker wins.
- **Native Windows instead of WSL2.** Models write bash, containers and OS-level sandboxing are Linux technologies, and CI runs on Linux. Native Windows would roughly double the complexity of every tool.

## Consequences

- **Types disappear at runtime.** Anything crossing a trust boundary — API responses, config files, tool arguments produced by a model — must be validated at runtime, not just typed.
- **Zod as the single source of truth for tool arguments.** One schema yields the TypeScript type (`z.infer`), the runtime validator, and the JSON Schema sent to the model (`z.toJSONSchema()`). Caveat: not everything Zod can express maps to JSON Schema (transforms, custom refinements), and providers accept only a subset of JSON Schema. Tool schemas stay simple, and each one is checked by a test that converts it.
- **Validation happens at the edges.** Adapters parse untrusted input into typed values; the core receives already-validated data. Whether the core's `Tool` interface depends on Zod directly or on a neutral schema type is decided in Phase 2.
- **Structural typing:** an object satisfies an interface if it has the right shape. No `implements` keyword is required, but adapters should use it anyway, so the compiler checks them against their port at the definition site.
- **No DI container.** Dependencies are passed through constructors and wired by hand in `src/main.ts`.
- **Discriminated unions** model messages and events (`{ type: "text_delta", … } | { type: "tool_start", … }`), with exhaustive `switch` checks so a new event type breaks compilation wherever it isn't handled.
- **Lint rules that must be on from day one:** `@typescript-eslint/no-floating-promises` and `@typescript-eslint/no-misused-promises` (async code), and `no-restricted-imports` forbidding `src/core/` from importing `src/adapters/` (enforces ADR-0001).
- **Type-checked linting is slower**, because it runs the TypeScript compiler. Acceptable at this project's size; revisit if lint time becomes annoying.
- **Prettier owns formatting; ESLint owns correctness.** Disable ESLint's formatting rules (`eslint-config-prettier`) so the two never conflict.
- **TypeScript is pinned to 6.0.x for now.** TypeScript 7 (the native rewrite of the compiler) is the current release, but typescript-eslint 8.71 only supports TypeScript below 6.1 (checked 2026-10-02). Move to 7 once typescript-eslint supports it; until then, `pnpm add -D typescript@latest` must not be run blindly.
